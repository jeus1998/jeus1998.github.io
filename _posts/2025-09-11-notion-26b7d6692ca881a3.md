{% raw %}# MacOS 레디스 설치하기

**HomeBrew를 사용해 레디스 설치**

```bash
brew install redis
```

**레디스 설치 확인 및 버전 확인 방법**

```bash
# 설치 확인
brew list redis

# 버전 확인 
redis-server --version
redis-cli --version
```

**레디스 서버 시작 및 종료**

```bash
# 서버 포그라운드 시작
redis-server

# 서버 백그라운드 시작
brew services start redis

# 서버 종료
brew services stop redis

# 서버 실행 상태 확인
brew services info redis
```

# 소켓과 파일 디스크립터 정리

## 1. 파일 디스크립터(File Descriptor)란?

**운영체제가 열린 파일이나 입출력 리소스를 식별하는 정수 값**

```
프로세스
├── fd 0: stdin  (표준 입력)
├── fd 1: stdout (표준 출력) 
├── fd 2: stderr (표준 에러)
├── fd 3: 파일/소켓
├── fd 4: 파일/소켓
└── ...
```

  - **Unix/Linux에서는 모든 것을 파일로 취급 → 네트워크 소켓도 파일 디스크립터로 관리**
  - 각 소켓 = 하나의 파일 디스크립터

## 2. 서버의 소켓 구조

### 각 서비스마다 독립적인 리스너 소켓

```
맥북 (물리적 서버)
├── MySQL 프로세스
│   ├── 리스너 소켓 1개 (포트 3306) → fd=10
│   ├── 클라이언트 연결 소켓 1 → fd=11  
│   └── 클라이언트 연결 소켓 2 → fd=12
├── Redis 프로세스
│   ├── 리스너 소켓 1개 (포트 6379) → fd=6
│   ├── 클라이언트 연결 소켓 1 → fd=7
│   └── 클라이언트 연결 소켓 2 → fd=8  
└── Spring 프로세스
    ├── 리스너 소켓 1개 (포트 8080) → fd=15
    └── 클라이언트 연결 소켓들...
```

## 3. Redis와 파일 디스크립터 관계

### 계산 공식

```
Redis가 사용하는 파일 디스크립터 =
├── 리스너 소켓: 1개
├── 클라이언트 연결: N개 (연결된 클라이언트 수)
├── 내부 파일: ~32개 (로그, RDB, AOF 등)
└── 기본: 3개 (stdin, stdout, stderr)
```

### Redis maxclients 설정

```
maxclients = 시스템 fd 제한 - 32
```

## 4. 소켓 식별 방법

**5-tuple로 각 소켓을 유니크하게 식별**

**<protocol, source IP, source Port, Destination IP, Destination Port>**

  - Protocol (TCP/UDP)
  - Source IP
  - Source Port
  - Destination IP
  - Destination Port

### 연결 예시

```
Spring → Redis 연결
127.0.0.1:랜덤포트 → 127.0.0.1:6379
```

## 5. 시스템 제한 관리

### 확인 명령어

```
# 파일 디스크립터 제한 확인
ulimit -n

# 전체 제한 확인  
ulimit -a

# 현재 사용량 확인
lsof -p $(pgrep redis-server) | wc -l
```

### 권장 설정

```
# Redis 운영 시 권장
ulimit -n 65536

# 계산: (예상 최대 클라이언트 × 1.2) + 100
```

## 6. 핵심 포인트

  - **1개 클라이언트 연결 = 1개 파일 디스크립터**
  - **각 서비스는 독립적인 리스너 소켓 보유**
  - **파일 디스크립터 제한을 높게 설정해도 실제 사용하지 않으면 리소스 소비 없음**
  - **시스템 제한 < Redis maxclients 설정 시 연결 거부 발생**

---

**레디스의 기본 maxclients 설정값: 10000**

→ 레디스 프로세스에서 받아들일 수 있는 최대 클라이언트의 개수를 의미

하지만 이 값은 레디스를 실행하는 서버의 파일 디스크립터 수에 영향을 받는다.

**레디스 프로세스 내부적으로 사용하기 위해 예약한 파일 디스크립터 수는 32개로, maxclients 값에 32를 더한 값보다 서버의 최대 파일디스크립터 수가 작으면 레디스는 실행될 때 자동으로 그 수에 맞게 조정**된다.

레디스의 최대 클라이언트 수를 기본값인 10000으로 지정하고 싶으면 서버의 파일 디스크립터 수를 최대 10032 이상으로 지정해야 한다.

**파일 디스크립터 확인 방법**

```shell
# 현재 제한 확인
ulimit -n
ulimit -a | grep descriptor

# 하드 제한 확인  
ulimit -Hn
```

**현재 세션 파일 디스크립터 변경 방법**

```bash
# 15000으로 설정
ulimit -n 15000

# 확인
ulimit -n
```

**영구적으로 파일 디스크립터 변경 방법**

```bash
echo "ulimit -n 15000" >> ~/.zshrc
source ~/.zshrc
```

### THP 비활성화

## THP란?

**Transparent Huge Pages는 리눅스 커널의 메모리 관리 기능**으로, 일반적인 4KB 페이지 대신 2MB 크기의 큰 페이지를 자동으로 사용하여 메모리 관리 효율성을 높이려는 기술

### 이론적 장점

  - TLB(Translation Lookaside Buffer) 미스 감소
  - 메모리 커버리지 향상(같은 TLB 엔트리 수로 512배 더 많은 메모리 커버)

## Redis에서 THP 비활성화 이유

### 1. 메모리 할당 지연(Memory Allocation Latency)

  - 큰 페이지 할당을 위한 메모리 조각 모음(defragmentation) 발생
  - 예측할 수 없는 지연시간으로 Redis 응답 시간 불안정

### 2. Copy-on-Write 문제

  - Redis RDB 스냅샷용 fork()시 문제 발생
  - 작은 데이터 변경에도 전체 2MB 페이지 복사 필요
  - 메모리 사용량 급증 및 성능 저하

### 3. 메모리 단편화

  - 내부 단편화 증가 (2MB 페이지를 다 사용하지 않는 경우)
  - 외부 단편화 재등장 (연속된 2MB 공간 확보 어려움)

### 4. 예측 불가능한 성능

  - THP 동적 할당/해제로 인한 성능 변동
  - 실시간성이 중요한 Redis에 치명적

## THP 비활성화 방법

```bash
# 즉시 비활성화
echo never > /sys/kernel/mm/transparent_hugepage/enabled

# 부팅 시 자동 비활성화 (GRUB 설정)
# /etc/default/grub 파일에 추가
GRUB_CMDLINE_LINUX_DEFAULT="transparent_hugepage=never"
```

## 페이지 시스템과 THP의 철학적 모순

### 페이지 시스템의 원래 목적

  - 고정 크기(4KB) 페이지로 메모리 균등 분할
  - 외부 단편화 완전 제거, 내부 단편화 최대한 제거
  - 예측 가능하고 효율적인 메모리 할당/해제

### THP의 모순점

  1. **외부 단편화 재등장**: 연속된 2MB 공간 확보의 어려움
  1. **철학적 모순**: "작고 균등하게" vs "크게 합치기"
  1. **복잡성 증가**: 4KB와 2MB 페이지 동시 관리 필요

## TLB 효율성 vs 메모리 관리 복잡성

### TLB 커버리지 비교

```
TLB 엔트리 64개 기준
- 4KB 페이지: 64 × 4KB = 256KB 메모리 커버
- 2MB 페이지: 64 × 2MB = 128MB 메모리 커버
→ 512배 차이
```

### 성능 트레이드오프

**장점**

  - TLB 효율성 대폭 향상
  - 메모리 집약적 애플리케이션에서 성능 개선

**단점:**

  - 메모리 단편화
  - 할당 지연
  - 예측 불가능한 성능
  - 내부 단편화

## 결론

THP는 "TLB 캐시 효율 vs 메모리 관리 복잡성"의 트레이드오프. 고성능 컴퓨팅에서는 효과적일 수 있지만, Redis처럼 **일관된 응답시간이 중요한 시스템**에서는 예측 불가능성이 더 큰 문제가 되어 비활성화가 권장된다.

### vm.overcommit_memory = 1로 변경

| 항목 | 0 (Heuristic) | 1 (Always) | 2 (Never) |
| --- | --- | --- | --- |
| **정책명** | **휴리스틱 오버커밋** | **항상 오버커밋 허용** | **엄격한 메모리 제한** |
| **기본값** | **default** | **수동 설정 필요** | **수동 설정 필요** |
| **할당 기준** | **커널이 "합리적" 판단** | **요청 시 무조건 허용** | **엄격 제한** |
| **메모리 제한** | **물리메모리 + 스왑(대략적)** | **제한 없음** | **물리메모리 × ratio + 스왑** |
| **Redis fork() 성공률** | **🟡 중간(메모리 상황에 따라)** | **🟢 높음(거의 항상 성공)** | **🔴 낮음(보수적 할당)** |
| **OOM 위험도** | **🟡 중간** | **🔴 높음** | **🟢 낮음** |
| **시스템 안정성** | **🟡 보통** | **🔴 위험할 수 있음** | **🟢 매우 안정** |
| **성능** | **🟡 보통** | **🟢 좋음** | **🟡 제한적** |

레디스는 **디스크에 파일을 저장할 때 fork()를 이용해 백그라운드 프로세스**를 만드는데, 이때 **COW(Copy On Write)라는 메커니즘이 동작**한다.

부모 프로세스와 자식 프로세스가 동일한 메모리 페이지를 공유하다가 **레디스의 데이터가 변경될 때마다 메모리 페이지를 복사하기 때문에 데이터 변경이 많이 발생하면 메모리 사용량이 빠르게 증가할 수 있다.**

따라서 레디스 프로세스가 실행되는 도중 메모리를 순간적으로 초과해 할당해야 하는 상황이 발생할 수 있다.

이때 vm.overcommit_memory=0이면 포크에 실패한다.

```bash
Redis 프로세스 (8GB 사용)
        ↓ fork()
부모 프로세스 (8GB) + 자식 프로세스 (8GB 예약)
        ↓ COW 동작
실제로는 변경된 페이지만 복사 (훨씬 적은 메모리 사용)
```

**Redis의 fork() + COW 패턴에서는 일시적으로 많은 메모리를 예약해야 하지만 실제로는 점진적으로 사용하기 때문에, vm.overcommit_memory=1 설정이 합리적인 선택이다.**

### somaxconn과 syn_backlog 설정 변경

### somaxconn

- **역할**: **완료된 TCP 연결을 저장하는 큐 크기 제한**
- **저장 대상**: 3-way handshake 완료 후 **accept()** 호출을 대기하는 **연결(connection)**
- **위치**: **/proc/sys/net/core/somaxconn**
- **기본값**: 128 또는 4096

### syn_backlog (tcp_max_syn_backlog)

- **역할**: **TCP handshake 진행 중인 미완료 연결 저장 큐**
- **저장 대상**: **SYN_RECEIVED 상태의 진행중인 연결(SYN → ACK + SYN 이후 클라이언트 응답 대기)**
- **위치**: **/proc/sys/net/ipv4/tcp_max_syn_backlog**
- **기본값**: 1024

## 연결 처리 흐름

```
클라이언트 연결 시도
    ↓
syn_backlog 큐 (handshake 진행) 
    ↓
somaxconn 큐 (연결 완료, accept() 대기)
    ↓
실제 데이터 통신 시작
```

## 설정 변경

### 임시 변경

```bash
echo 65535 > /proc/sys/net/core/somaxconn
echo 65535 > /proc/sys/net/ipv4/tcp_max_syn_backlog
```

### 영구 변경

**/etc/sysctl.conf**에 추가

```
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
```

## 레디스 설정 파일 변경

**설정파일: redis.conf**

```bash
open -a TextEdit /opt/homebrew/etc/redis.conf
```

### port

**default: 6379**

커넥션이 지정된 포트로 레디스 서버에 접속할 수 있도록 허용한다.

### bind

**default: 127.0.0.1 ::1**

레디스가 설치된 서버 외부에서 레디스 인스턴스로 바로 접근하는 것을 허용하기 위해서는 해당 설정값을 변경해야 한다.

```bash
bind 192.168.1.100 127.0.0.1
```

해당 설정값의 경우 192.168.1.100과 127.0.0.1 IP 주소로 들어오는 연결을 허용함을 의미한다.

### protected-mode

**default: yes**

패스워드를 설정해야만 레디스에 접근할 수 있으며, 패스워드가 설정돼 있지 않다면 서버는 오직 로컬에서 들어오는 연결만 수신할 수 있다.

### requirepass / masterauth

**default: 없음** 

**requirespass:** 서버에 접속하기 위한 패스워드 값을 의미한다.

**masterauth:** 복제 구조를 사용할 때 필요하다. 연결될 마스터의 패스워드 값을 의미한다. 만약 복제 연결을 사용할 예정이라면 이 두 값은 같은 값으로 설정하는 것이 좋다.

### **daemonize**

**default: no**

레디스 프로세스를 데몬으로 실행시키려면 yes로 변경해야 한다.

레디스를 데몬으로 실행하면 백그라운드에서 실행되고, pid 파일이 생성된다.

### dir

**default: ./**

레디스의 워킹 디렉터리를 의미한다. 로그 파일이나 백업 파일 등 인스턴스를 실행하면서 만들어지는 파일은

기본적으로 해당 파라미터에서 지정한 디렉터리에 저장되므로 특정 값을 지정해주는 것이 좋다.
