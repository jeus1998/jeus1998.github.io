# 1.플러그인(Plugin)

## 1-1. 플러그인(Plugin)?

```kotlin
plugins {
    id("org.springframework.boot") version "3.2.3"
    kotlin("jvm") version "2.2.20"
    kotlin("plugin.spring") version "1.8.0"
    id("io.spring.dependency-management") version "1.0.15.RELEASE"
}
```

**플러그인 → 미리 만들어진 기능 모음**

Gradle에서 플러그인은 **빌드 작업을 자동화해주는 도구 세트**이다.

플러그인이 제공하는 것들

```plain text
플러그인 설치 → 다음 것들이 자동으로 추가
├── Task (작업들): build, test, run 등
├── 설정: 컴파일 옵션, 실행 방법 등
└── 의존성 관리: 필요한 라이브러리 자동 추가
```

## 1-2. id?

`id` = 플러그인의 고유한 이름(식별자)

```kotlin
id("org.springframework.boot") // 해당 플러그인의 고유 이름
```

**플러그인 이름 작성 방식1: 전체 이름 (Full ID)**

```kotlin
id("org.springframework.boot") version "3.2.3"
```

  - `org.springframework.boot` : 플러그인 전체 이름

**플러그인 이름 작성 방식2: 축약형(Kotlin DSL 전용)**

```kotlin
kotlin("jvm") version "2.2.20"
```

  - `kotlin("jvm")`은 `id("org.jetbrains.kotlin.jvm")`  축약형
  - Kotlin 관련 플러그인만 이렇게 짧게 쓸 수 있다.

**즉, 아래의 두 방식은 완전히 동일하다**

```kotlin
kotlin("jvm") version "1.9.0"
id("org.jetbrains.kotlin.jvm") version "1.9.0"

kotlin("plugin.spring") version "1.9.0"
id("org.jetbrains.kotlin.plugin.spring") version "1.9.0"
```

## 1-3. version?

`version` 플러그인의 버전 번호

```plain text
id("org.springframework.boot") version "3.2.3"
                                        ↑
                                    이 플러그인의 버전

**버전 번호 읽는 법**

3.2.3
│ │ │
│ │ └── Patch (패치): 버그 수정
│ └──── Minor (마이너): 새 기능 추가 (하위 호환)
└────── Major (메이저): 큰 변화 (호환성 깨질 수 있음)
```

  - 3.2.3 → 3.2.4: 작은 버그 수정
  - 3.2.3 → 3.3.0: 새 기능 추가
  - 3.2.3 → 4.0.0: 대대적인 변경, 이전 버전과 호환 안 될 수 있다

## 1.4 플러그인 분석

```kotlin
id("org.springframework.boot") version "3.2.3"
```

  - SpringBoot 애플리케이션을 실행 가능한 JAR로 만들어준다
  - `./gradlew bootRun`  명령으로 앱 실행 가능
  - SpringBoot 관련 설정 자동화

```kotlin
kotlin("jvm") version "2.2.20"
```

  - Kotlin JVM 플러그인 축약형, 실제 이름: `org.jetbrains.kotlin.jvm` 
  - `.kt` 파일(Kotlin 파일)을 `.class`  파일(Java 바이트 코드)로 변환
  - JVM에서 실행 가능한 형태로 컴파일
```plain text
MyApp.kt (Kotlin 코드)
    ↓
[Kotlin 컴파일러]  ← 이 플러그인이 제공
    ↓
MyApp.class (바이트코드)
    ↓
JVM에서 실행 가능
```

```kotlin
kotlin("plugin.spring") version "1.8.0"
```

  - **Kotlin과 Spring 궁합 문제를 해결**
  - 어떤 문제?
```kotlin
// Kotlin 클래스는 기본적으로 final (상속 불가)
class UserService {  
    fun getUser() { }
}
```

**Spring 요구사항**

    - Spring은 프록시(대리자)를 만들기 위해 클래스를 상속해야 함
    - 하지만 Kotlin 클래스는 기본이 `final`이라 상속 불가능

**플러그인의 해결책**

```kotlin
// 자동으로 변환됨
@Component
open class UserService {       // 자동으로 open 추가
    open fun getUser() { }
}
```

    - 특정 Spring 애노테이션이 붙은 클래스를 자동으로 `open`  추가
    - @Component, @Service, @Repository, @Configuration, @Controller, @RestController

```kotlin
id("io.spring.dependency-management") version "1.0.15.RELEASE"
```

  - Spring 의존성 관리 플러그인
  - 즉, 의존성의 버전을 자동으로 관리해준다.

# 2. group, version, repositories

## 2-1. group(그룹 ID)?

```kotlin
group = "study"
```

**group 이란 프로젝트를 구분하는 주소 같은 것**

**비유로 이해**

```kotlin
**실제 주소 example**
대한민국 > 서울시 > 강남구 > 아파트 > 101호

Maven/Gradle에서도 비슷하다.

group > name > version
----------------------------------------------------------------------------
**실제 예시**

1) Spring Framework 라이브러리
- group: org.springframework
- name: spring-core
- version: 6.1.4

-> 전체 좌표: org.springframework:spring-core:6.1.4

2) Google Guava 라이브러리
- group: com.google.guava
- name: guava
- version: 32.1.0

-> 전체 좌표: com.google.guava:guava:32.1.0

3) 현재 프로젝트
- group: study
- name: (프로젝트 이름, settings.gradle.kts에 정의됨)
- version: 1.0-SNAPSHOT

-> 전체 좌표: study:프로젝트이름:1.0-SNAPSHOT
```

## 2-2. version(버전)

```kotlin
version = "1.0-SNAPSHOT"
```

**version은 프로젝트의 현재 버전을 나타내는 번호**

**버전 표기법**

```kotlin
1.0-SNAPSHOT
│ │  │
│ │  └─── 개발 중 (아직 완성 안됨)
│ └────── Minor version
└──────── Major version
```

  - SNAPSHOT 있음: 개발 버전을 의미한다, 아직 개발 중, 배포하지 않음
  - SNAPSHOT 없음: 릴리스 버전, 정식 출시 버전, 외부에 배포

## 2-3. repositories(저장소)

```kotlin
repositories {
    mavenCentral()
}
```

**repositories?** 

→ 라이브러리(의존성)를 다운로드할 장소를 지정한다.

**mavenCentral() - 가장 많이 사용**

  - 공식 Maven 중앙 저장소
  - 전 세계 오픈소스 라이브러리 대부분 여기 있다
  - Spring Framework, Kotlin 라이브러리, Jackson, JUnit …

**여러 저장소 사용하기**

```kotlin
repositories {
    mavenCentral()  // 1순위: 여기서 먼저 찾음
    google()        // 2순위: 없으면 여기서 찾음
    mavenLocal()    // 3순위: 그래도 없으면 로컬에서 찾음
}

검색 순서

의존성 필요!
    ↓
1. mavenCentral() 검색
    ↓ (없으면)
2. google() 검색
    ↓ (없으면)
3. mavenLocal() 검색
    ↓ (없으면)
❌ 에러 발생!
```

# 3. dependencies

## **3-1. dependencies?**

내 프로젝트가 사용할 외부 라이브러리(의존성)를 선언하는 곳

**의존성 선언 형식**

```kotlin
의존성타입("그룹:이름:버전")

implementation("org.springframework.boot:spring-boot-starter-web:3.2.3")
     ↓                  ↓                         ↓                ↓
    타입              그룹(group)                이름(name)       버전(version)
```

### 의존성 타입(Configuration) 개념

왜 여러 타입이 필요할까?

→ **라이브러리를 언제, 어디서 사용할지 구분하기 위해서**

**시점별 구분**

  - 컴파일 시점(코드 작성 & 빌드)
  - 런타임 시점(프로그램 실행)
  - 테스트 시점(테스트 코드 실행)

**공개 범위 구분**

  - 내 모듈만 사용(private)
  - 다른 모듈도 사용 가능(public)

## 3-2. 주요 의존성 타입 상세 설명

### 3-2-1. implementation

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web:3.2.3")
}
```

**implementation 특징**

```plain text
컴파일할 때도 필요하고, 실행할 때도 필요 -> compile time + run time 
다른 모듈에는 노출되지 않음(캡슐화) -> module private

**언제 사용?**
- 대부분의 일반적인 라이브러리
- 내 프로젝트에서만 사용하는 것
```

**implementation example(동작 방식 설명)**

```kotlin
**프로젝트 구조**
app(모듈)
  └─ depends on → library(모듈)

**library/build.gradle.kts**
dependencies {
    implementation("com.google.gson:gson:2.10.1")
}

--------------------------------------------------------------------------------
**library/Library.kt** 
import com.google.gson.Gson  // ✅ 사용 가능

class Library {
    fun process() {
        val gson = Gson()
    }
}

--------------------------------------------------------------------------------
**app/App.kt**
import com.google.gson.Gson  // ❌ 에러! Gson을 볼 수 없음
import Library  // ✅ Library는 사용 가능

class App {
    val lib = Library()  // OK
    // val gson = Gson()  // 컴파일 에러!
}
--------------------------------------------------------------------------------
**왜 이렇게?
1. 빌드 속도 향상 (library가 변경되어도 app은 재컴파일 안 함)
2. 의존성 숨기기(내부 구현 감추기)**
```

### 3-2-2. api

```kotlin
dependencies {
    api("com.google.code.gson:gson:2.10.1")
}
```

**api 특징**

```kotlin
**의미**
- 컴파일 + 런타임에 필요
- 다른 모듈에도 노출됨(전파)

**언제 사용?**
- 라이브러리의 타입이 public API에 노출될 때
- 다른 모듈도 같이 사용해야 할 때
```

```kotlin
**library/build.gradle.kts**
dependencies {
    api("com.google.code.gson:gson:2.10.1")  
}

--------------------------------------------------------------------------------
**library/Library.kt**
import com.google.gson.Gson

class Library {
    fun getGson(): Gson {
        return Gson()
    }
}
--------------------------------------------------------------------------------
**app/App.kt**
import com.google.gson.Gson  // ✅ 이제 사용 가능
import Library

class App {
    val lib = Library()
    val gson: Gson = lib.getGson()  // ✅ Gson 타입 사용 가능
}
```

### 3-2-3. compileOnly(컴파일만)

```kotlin
dependencies {
    compileOnly("org.projectlombok:lombok:1.18.30")
}
```

**compileOnly 특징**

```plain text
**의미**
- 컴파일할 때만 필요
- 실행할 때는 포함되지 않음

**언제 사용**
- 코드 생성 도구 (Lombok)
- 컴파일 시점에만 필요한 애노테이션
- 실행 환경이 제공하는 라이브러리
```

**example: Lombok**

```kotlin
dependencies {
    compileOnly("org.projectlombok:lombok:1.18.30")
}
--------------------------------------------------------------------------------
import lombok.Data;

@Data  // getter, setter 자동 생성
public class User {
    private String name;
    private int age;
}
--------------------------------------------------------------------------------
**컴파일 과정**

1. 컴파일 시점
   @Data 어노테이션 → Lombok이 코드 생성
   
2. 생성된 .class 파일
public class User {
   private String name;
   private int age;
   
   public String getName() { ... }     // 자동 생성됨
   public void setName(String name) { ... }
   // ... 등등
}
   
3. 실행 시점
이미 코드가 생성되어 있으므로 Lombok 불필요!
```

### 3-2-4. runtimeOnly(실행만)

```kotlin
dependencies {
    runtimeOnly("com.h2database:h2:2.2.220")
}
```

**runtimeOnly 특징**

```plain text
**의미**
- 컴파일할 때는 필요 없음
- 실행할 때만 필요

**언제 사용?**
- 데이터베이스 드라이버
- 로깅 구현체
- 실행 시점에 동적으로 로드되는 라이브러리
```

**example: 데이터베이스 드라이버**

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-jdbc")
    runtimeOnly("com.h2database:h2")  // H2 드라이버
}
--------------------------------------------------------------------------------
**DataService.kt**
import java.sql.DriverManager

class DataService {
    fun connect() {
        // H2 클래스를 직접 import 하지 않음!
        // 하지만 실행 시 DriverManager가 자동으로 H2를 찾아서 사용
        val conn = DriverManager.getConnection("jdbc:h2:mem:test")
    }
}
--------------------------------------------------------------------------------
**왜 runtimeOnly?**

컴파일 시점
- H2 클래스를 직접 사용 안 함
- JDBC 표준 인터페이스만 사용

실행 시점
- DriverManager가 classpath에서 H2를 찾음
- H2 드라이버를 동적으로 로드
```

### 3-2-5. testImplementation(테스트용)

```kotlin
dependencies {
    testImplementation(kotlin("test"))
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.0")
}
```

**testImplementation 특징**

```plain text
**의미**
- 테스트 코드에서만 사용
- 본 코드나 실행 JAR에는 포함 안 됨

**언제 사용?**
- JUnit, Mockito 같은 테스트 프레임워크
- 테스트 전용 라이브러리

**프로젝트 구조**
src/
├── main/
│   └── kotlin/
│       └── MyService.kt         ← testImplementation 사용 불가
└── test/
    └── kotlin/
        └── MyServiceTest.kt     ← testImplementation 사용 가능
```

**example**

```kotlin
**src/main/kotlin/MyService.kt**
class MyService {
    fun add(a: Int, b: Int) = a + b
}
--------------------------------------------------------------------------------
**src/test/kotlin/MyServiceTest.kt**
import org.junit.jupiter.api.Test   
import org.junit.jupiter.api.Assertions.*

class MyServiceTest {
    @Test
    fun 더하기 테스트() {
        val service = MyService()
        assertEquals(3, service.add(1, 2))
    }
}
--------------------------------------------------------------------------------
**빌드 결과**
./gradlew build 실행 시

build/libs/myapp.jar
├── MyService.class           ← 포함됨
├── spring-boot-*.jar         ← 포함됨
└── junit-jupiter-*.jar       ← 포함 안 됨! (테스트만 사용)
```

| 타입 | 컴파일 시 | 런타임 시 | 다른 모듈 노출 | 테스트 전용 |
| --- | --- | --- | --- | --- |
| **implementation** | ✅ | ✅ | ❌ | ❌ |
| **api** | ✅ | ✅ | ✅ | ❌ |
| **compileOnly** | ✅ | ❌ | ❌ | ❌ |
| **runtimeOnly** | ❌ | ✅ | ❌ | ❌ |
| **testImplementation** | ✅ | ✅ | ❌ | ✅ |
| **testCompileOnly** | ✅ | ❌ | ❌ | ✅ |
| **testRuntimeOnly** | ❌ | ✅ | ❌ | ✅ |

**회의 주요 용어 정리**

| **용어** | **정리** |
| --- | --- |
| **산출물 (Deliverable)** | 프로젝트 수행 과정에서 작성·제출하는 문서 또는 결과물. 예: 요구사항 정의서, 설계서, WBS, 테스트 문서 등. |
| **테일러링 (Tailoring)** | 표준 방법론과 산출물을 해당 프로젝트 상황에 맞게 선택·수정·조정하는 작업. 즉, 어떤 산출물을 누가 언제 어떤 양식으로 작성할지 정하는 과정. |
| **WBS** | Work Breakdown Structure. 프로젝트 업무를 세부 작업 단위로 분해하여 일정, 담당자, 진행상태 등을 관리하는 체계. |
| **PL** | Project Leader. 특정 업무 영역이나 실무 파트를 이끌고 관리하는 역할. |
| **PM** | Project Manager. 프로젝트 전체 일정, 인력, 이슈, 고객 커뮤니케이션 등을 총괄하는 역할. |
| **PMO** | Project Management Office. 일정, 보고, 회의록, Risk, Action Item, 산출물 등 프로젝트 관리 체계를 지원·관리하는 역할. |
| **CBT** | 일반적으로 Closed Beta Test. 정식 오픈 전 제한된 사용자 또는 환경에서 시스템을 검증하는 단계. 프로젝트 내 별도 정의가 있는 경우 해당 정의를 우선 확인. |
| **Risk** | 프로젝트 일정, 품질, 범위 등에 영향을 줄 가능성이 있는 잠재적 위험요소. |
| **Risk History** | Risk의 식별 시점, 원인, 대응 내용, 상태 변화, 종료 여부 등을 지속적으로 기록·추적하는 것. |
| **Action Item** | 회의에서 결정된 후속 실행 과제. 담당자, 목표일, 진행상태를 함께 관리하는 것이 일반적. |
| **Follow-up** | 이전에 논의하거나 지시한 업무·이슈가 어떻게 진행되고 있는지 지속적으로 확인하고 후속 조치하는 것. |
| **서브 프로젝트** | 전체 프로젝트를 업무 영역, 시스템, 조직 등의 기준으로 나눈 하위 프로젝트. |
| **착수보고** | 프로젝트 초기에 수행 범위, 추진계획, 일정, 조직 및 관리방안 등을 고객에게 공식적으로 보고하는 절차. |
| **주간보고** | 주 단위로 진행 현황, 차주 계획, 이슈, Risk, Action Item 등을 공유하는 보고. |
| **월간보고** | 월 단위로 프로젝트의 전체 진행 현황과 주요 이슈 및 계획을 공유하는 보고. |
| **HR** | Human Resources. 본 회의에서는 인사 데이터 또는 인사 시스템 관련 영역을 의미. |
| **배치 (Batch)** | 정해진 시간 또는 조건에 따라 데이터를 일괄 처리하는 프로그램이나 작업. 예: 인사 데이터 정기 연계 및 반영. |
