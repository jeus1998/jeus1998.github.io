### 방법1 - 개인 프로젝트에서 많이 쓰는 CI/CD 구축 방법 (Github Actions)

### ✅ 전체적인 흐름

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca88191bcedd6dd97313270.png)

### ✅ 장점

      - git pull을 활용해서 변경된 부분의 프로젝트 코드에 대해서만 업데이트 하기 때문에 CI/CD 속도가 빠르다. 
- 대부분의 CI/CD 방식들은 전체 프로젝트를 통째로 갈아끼우는 방식을 사용한다.
      - CI/CD 툴로 Github Actions만 사용하기 때문에 인프라 구조가 복잡하지 않고 간단하다. 

### ✅ 단점

      - 빌드 작업을 EC2에서 직접 진행하기 때문에 운영하고 있는 서버의 성능에 영향을 미칠 수 있다. 
- 운영 서버에서 빌드를 하면 CPU, 메모리가 많이 소모된다.
      - Github 계정 정보가 해당 EC2에 저장되기 때문에 개인 프로젝트 또는 믿을만한 사람들과 같이 진행하는 토이 프로젝트에서만 사용해야 한다. 
```shell
ls -a 
cat .git-credentials
```

        - 이렇게 private repository 통한 프로젝트를 진행하면 매번 깃허브 access token 넣기가 귀찮아서 
ec2 서버에 저장하는데 github 정보 주인이 아닌 다른 ec2에 접속 가능한 팀원이 볼 수 있다. 
        - 간단한 해결 방법은 public repository로 프로젝트를 진행 
        - 토큰 권한을 제한

### ✅ 이 방법은 언제 주로 쓰는 지

# **Actions 작성** 

**.github/workflows [경로]**

```yaml
name: Deploy to EC2

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: SSH 사용하여 EC2 접속 및 배포
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.EC2_HOST }} # EC2의 주소
          username: ${{ secrets.EC2_USERNAME }} # EC2 접속 username
          key: ${{ secrets.EC2_PRIVATE_KEY }} # EC2의 Key 파일
          script_stop: true # 실패하면 전체 실패 처리
          script: |
            
            cd /home/ubuntu/CI-CD-study
            
            # 최신 코드 가져오기
            git pull origin main 
            
            # 프로젝트 빌드
            ./gradlew clean build 
            
            # 실행 중인 애플리케이션 종료 (서버가 실행 중이 아니어도 에러 없이 통과)
            sudo fuser -k -n tcp 8080 || true
            
            # 종료 대기 (3초)
            sleep 3
            
            # *SNAPSHOT.jar 끝나는 빌드 파일로 애플리케이션 실행 output.log 로그 기록 
            nohup java -jar build/libs/*SNAPSHOT.jar > ./output.log 2>&1 &
            
            # 배포 완료

```

### **Gitbub Actions 코드 수정하기**

      - **.github/workflows/deploy.yml**

```yaml
name: Deploy to EC2

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: SSH 사용하여 EC2 접속 및 배포
        uses: appleboy/ssh-action@v1.0.3
        env:
          APPLICATION_PROPERTIES: ${{ secrets.APPLICATION_PROPERTIES }}
        with:
          host: ${{ secrets.EC2_HOST }} # EC2의 주소
          username: ${{ secrets.EC2_USERNAME }} # EC2 접속 username
          key: ${{ secrets.EC2_PRIVATE_KEY }} # EC2의 Key 파일
          envs: APPLICATION_PROPERTIES
          script_stop: true # 실패하면 전체 실패 처리
          script: |
            cd /home/ubuntu/CI-CD-study
            
            rm -rf src/main/resources/application.yml
            
            # 최신 코드 가져오기
            git pull origin main 
            
            echo "$APPLICATION_PROPERTIES" > src/main/resources/application.yml
            
            # 프로젝트 빌드
            ./gradlew clean build 
            
            # 실행 중인 애플리케이션 종료 (서버가 실행 중이 아니어도 에러 없이 통과)
            sudo fuser -k -n tcp 8080 || true
            
            # 종료 대기 (3초)
            sleep 3
            
             # *SNAPSHOT.jar 끝나는 빌드 파일로 애플리케이션 실행 output.log 로그 기록 
            nohup java -jar build/libs/*SNAPSHOT.jar > ./output.log 2>&1 &
            
            # 배포 완료

```

      - GitHub Actions 환경 변수로 등록
```yaml
env:
  APPLICATION_PROPERTIES: ${{ secrets.APPLICATION_PROPERTIES }}
```
      - SSH 액션(`appleboy/ssh-action`)에 환경 변수를 전달
```yaml
with:
  envs: APPLICATION_PROPERTIES
```

        - `envs` 키워드를 사용하여 `APPLICATION_PROPERTIES` 환경 변수를 SSH 세션에서도 사용할 수 있도록 설정
        - SSH 내부에서 `$APPLICATION_PROPERTIES`로 접근 가능하게 된다.
      - script 활용 
```yaml
 echo "$APPLICATION_PROPERTIES" > src/main/resources/application.yml
```

        - `$APPLICATION_PROPERTIES` 값을 **`src/main/resources/application.yml`** **파일로 저장**하는 역할을 한다.
        - 즉, GitHub Actions의 `secrets`에 저장된 설정 값을 EC2 서버로 전달하여 `application.yml`을 생성하는 방식이다.

### 방법2 - 일반 프로젝트에서 많이 쓰는 CI/CD 구축 방법 (Github Actions, SCP)

### ✅ 전체적인 흐름

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca881eb9777fe0aa1f23168.png)

### ✅ 방법1과 차이점

      - 프로젝트 빌드를 Github Actions에서 하고 AWS EC2에 전달한다. 

### ✅ 장점

      - 빌드 작업을 Github Actions에서 하기 때문에 운영하고 있는 서버의 성능에 영향을 거의 주지 않는다. 
      - CI/CD 툴로 Github Actions만 사용하기 때문에 인프라 구조가 복잡하지 않고 간단하다. 

### ✅ 단점

      - 무중단 배포를 구현하거나 여러 EC2 인스턴스에 배포를 해야 하는 상황이라면, 직접 Github Actions에 스크립트를 작성해서 구현해야 한다. 직접 구현을 해보면 알겠지만 생각보다 꽤 복잡하다. 

### ✅ 이 방법은 언제 주로 쓰는 지

      - 현업에서 초기 서비스를 구축할 때 이 방법을 많이 활용한다. 
- 처음 서비스를 구현할 때는 대규모 서비스에 적합한 구조로 구현하지 않는다. 즉, 오버 엔지니어링을 하지 않는다. 확장의 필요성이 있다고 느끼는 시점에 인프라를 고도화하기 시작한다. 왜냐하면 복잡한 인프라 구조를 갖추고 관리하는 건 생각보다 **여러 측면**에서 신경쓸 게 많아지기 때문이다. 
- 인프라 구조를 변경할 때 시간이 많이 들어감
          - 에러가 발생했을 때 트러블 슈팅의 어려움
          - 팀원이 인프라 구조를 이해하기 어려워 함
          - 기능을 추가하거나 수정할 때 더 많은 시간이 들어감
          - 금전적인 비용이 더 많이 발생

### **Github Actions 작성** 

```yaml
name: Deploy to EC2

on:
  push:
    branches:
      - main


jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Github Repository 올린 파일들 불러오기
        uses: actions/checkout@v4

      - name: JDK 17버전 설치
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17

      - name: application.yml 파일 만들기
        run: echo "$APPLICATION_PROPERTIES" > ./src/main/resources/application.yml

      - name: 테스트 및 빌드하기
        run: ./gradlew clean build

      - name: 빌드된 파일 이름 변경하기
        run: mv ./build/libs/*SNAPSHOT.jar ./project.jar

      - name: SCP 사용 EC2에 빌드된 파일 전송
        uses: appleboy/scp-action@v0.1.7
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ${{ secrets.EC2_USERNAME }}
          key: ${{ secrets.EC2_PRIVATE_KEY }}
          source: project.jar
          target: /home/ubuntu/backend-server/tobe

      - name: SSH 사용하여 EC2 접속 및 배포
        uses: appleboy/ssh-action@v1.0.3
        with:
          # EC2의 주소
          host: ${{ secrets.EC2_HOST }}
          # EC2 접속 username
          username: ${{ secrets.EC2_USERNAME }}
          # EC2의 Key 파일
          key: ${{ secrets.EC2_PRIVATE_KEY }}
          script_stop: true # 실패하면 전체 실패 처리
          script: |
            # 이전 폴더 삭제
            rm -rf /home/ubuntu/backend-server/current
            
            # 폴더 다시 생성 
            mkdir /home/ubuntu/backend-server/current
            
            # tobe -> current 빌드파일 이동 
            mv /home/ubuntu/backend-server/tobe/project.jar /home/ubuntu/backend-server/current/project.jar
            
            cd /home/ubuntu/backend-server/current
            
            # 실행 중인 애플리케이션 종료 (서버가 실행 중이 아니어도 에러 없이 통과)
            sudo fuser -k -n tcp 8080 || true
            
            # 종료 대기 (3초)
            sleep 3
            
            # 애플리케이션 실행 output.log 로그 기록 
            nohup java -jar project.jar > ./output.log 2>&1 &
            
            # 폴더 삭제 
            rm -rf /home/ubuntu/backend-server/tobe
            
            # 배포 완료

```

### 방법3 - 확장성을 고려한 프로젝트에서 많이 쓰는 CI/CD 구축 방법(CodeDeploy)

### ✅ 전체적인 흐름

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca881a3adacd57af9bb8a04.png)

### ✅ CodeDeploy를 사용하는 이유

      - CodeDeploy는 수많은 AWS EC2에 배포를 쉽게 할 수 있도록 도와준다. 
      - CodeDeploy에 무중단 배포 기능이 내재되어 있어 손쉽게 무중단 배포를 진행할 수 있다. 

> 이 외에도 다양한 장점이 존재한다. 

[https://docs.aws.amazon.com/ko_kr/codedeploy/latest/userguide/welcome.html](https://docs.aws.amazon.com/ko_kr/codedeploy/latest/userguide/welcome.html)

### ✅ 장점

      - 서버가 여러 대이더라도 쉽게 자동 배포를 구축할 수 있다. 
      - 쉽게 무중단 배포를 적용시킬 수 있다. 

### ✅ 단점

      - CodeDeploy를 사용함으로써 인프라 구조가 복잡해졌다. 구조가 복잡해짐에 따라 관리 비용, 유지보수 비용, 난이도, 트러블 슈팅 어려움, 복잡도가 증가했다. 

### ✅ 이 방법은 언제 주로 쓰는 지

      - 서버를 여러 대 이상 구동해야 하거나 무중단 배포가 중요한 서비스일 때 주로 활용한다.

```shell
cd /home/ubuntu && \
wget https://aws-codedeploy-ap-northeast-2.s3.ap-northeast-2.amazonaws.com/latest/install && \
```

# Github Actions 사용자 부여

      - **S3, CodeDeploy**에 접근하려면 권한이 필요하다. 
      - **CodeDeploy** → **EC2** 같은 접근은 같은 AWS 자원끼리의 접근이다. 
      - **Github Actions**은 외부 자원이다**.** 그래서 **역할**이 아닌 **사용자**를 부여한다.

### appspec.yml, 스크립트 파일 작성하기

      - appspec.yml은 CodeDeploy가 실행될 때 필수적으로 존재해야 하는 파일
      - CodeDeploy는 이 설정 파일을 기반으로 실행
      - 프로젝트 최상위 경로에 appspec.yml 생성

**appspec.yml**

```yaml
version: 0.0
os: linux

files:
    # S3에 저장한 파일들 중 destination(AWS EC2)으로 이동시킬 대상을 지정
    # /: S3 저장한 전체 파일
  - source: /
    # EC2의 어떤 경로에 저장할 지 지정
    destination: /home/ubuntu/backend-server

permissions:
  - object: /
    owner: ubuntu
    group: ubuntu

hooks:
  ApplicationStart:
    - location: scripts/start-server.sh
      timeout: 60
      runas: ubuntu 
```

      - ec2에 설치된 Code Deploy Agent가 실행 
      - S3에 저장된 빌드 파일 다운 
      - shell 파일 run 통해서 배포 

**scripts/start-server.sh**

```shell
#!/bin/bash

echo "--------------- 서버 배포 시작 -----------------"
cd /home/ubuntu/instagram-server
sudo fuser -k -n tcp 8080 || true
nohup java -jar project.jar > ./output.log 2>&1 &
echo "--------------- 서버 배포 끝 ------------------"
```

### Github Actions 코드 작성하기

```yaml
name: Deploy to EC2

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Github Repository 올린 파일들 불러오기
        uses: actions/checkout@v4

      - name: JDK 17버전 설치
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17

      - name: application.yml 파일 만들기
        run: echo "$APPLICATION_PROPERTIES" > ./src/main/resources/application.yml

      - name: 테스트 및 빌드하기
        run: ./gradlew clean build

      - name: 빌드된 파일 이름 변경하기
        run: mv ./build/libs/*SNAPSHOT.jar ./project.jar

      - name: 압축하기
        run: tar -czvf $GITHUB_SHA.tar.gz project.jar appspec.yml scripts

      - name: AWS Resource 접근할 수 있게 AWS credentials 설정
        uses: aws-actions/configure-aws-credentials@v4
        with:
           aws-region: ap-northeast-2
           aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
           aws-secret-access-key: [REDACTED] secrets.AWS_SECRET_ACCESS_KEY }}

      - name: S3에 프로젝트 폴더 업로드
        # study-server s3 버켓으로 복사(cp)
        run: aws s3 cp --region ap-northeast-2 ./$GITHUB_SHA.tar.gz s3://study-server/$GITHUB_SHA.tar.gz

      - name: Code Deploy 활용하여 EC2에 프로젝트 코드 배포
        run: aws deploy create-deployment
          --application-name study-server
          --deployment-config-name CodeDeployDefault.AllAtOnce
          --deployment-group-name Production
          --s3-location bucket=study-server,bundleType=tgz,key=$GITHUB_SHA.tar.gz
```

```yaml
- name: 압축하기
  run: tar -czvf $GITHUB_SHA.tar.gz project.jar appspec.yml scripts
```

      - `tar`: 유닉스/리눅스에서 파일 및 디렉토리를 아카이빙(묶기)하는 명령어
      - `c` (**create**) : 새로운 tar 아카이브 파일을 생성
      - `z` (**gzip**) : 아카이브 파일을 gzip 압축하여 `.tar.gz` 형태로 만듦
      - `v` (**verbose**) : 압축 과정에서 어떤 파일이 추가되는지 출력 (옵션이므로 생략 가능)
      - `f $GITHUB_SHA.tar.gz` (**file**) : 생성할 압축 파일 이름 (`$GITHUB_SHA`는 GitHub Actions에서 현재 커밋 SHA(commit ID 값이 들어감) 
      - `project.jar` : 배포할 애플리케이션 실행 파일 (Spring Boot 애플리케이션 등)
      - `appspec.yml` : AWS CodeDeploy 배포를 위한 설정 파일
      - `scripts` : 배포 및 실행을 위한 스크립트 디렉터리 (start-server.sh 포함)

```yaml
- name: Code Deploy 활용하여 EC2에 프로젝트 코드 배포
  run: aws deploy create-deployment
    --application-name study-server
    --deployment-config-name CodeDeployDefault.AllAtOnce
    --deployment-group-name Production
    --s3-location bucket=study-server,bundleType=tgz,key=$GITHUB_SHA.tar.gz
```

      - `--application-name study-server`
- CodeDeploy 애플리케이션 이름
      - `--deployment-config-name CodeDeployDefault.AllAtOnce`
- CodeDeploy 배포 구성
      - `--deployment-group-name Production`
- CodeDeploy 배포 그룹 이름
      - `--s3-location bucket=study-server,bundleType=tgz,key=$GITHUB_SHA.tar.gz`
- S3 버켓 이름,파일 이름

### ✅ 장점

      - Docker 기반으로 서비스를 운영할 때, 가장 간단하게 구성할 수 있는 인프라 구조이다. 

### ✅ 단점

      - 무중단 배포를 구현하거나 여러 EC2 인스턴스에 배포를 해야 하는 상황이라면, 직접 Github Actions에 스크립트를 작성해서 구현해야 한다. 직접 구현을 해보면 알겠지만 생각보다 꽤 복잡하다. 

### ✅ 이 방법은 언제 주로 쓰는 지

      - 컨테이너 기반으로 인프라를 구성했을 때 이 방법을 많이 활용한다. 
      - 서버를 여러 대 운영하고 있지 않을 정도의 소규모 프로젝트 일 때 주로 활용한다.

### Ubuntu에서 Docker, Docker Compose 설치하기

```shell
$ sudo apt-get update && \
sudo apt-get install -y apt-transport-https ca-certificates curl software-properties-common && \
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo apt-key add - && \
sudo apt-key fingerprint 0EBFCD88 && \
sudo add-apt-repository "deb [arch=amd64] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" && \
sudo apt-get update && \
sudo apt-get install -y docker-ce && \
sudo usermod -aG docker ubuntu && \
sudo curl -L "https://github.com/docker/compose/releases/download/1.23.2/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose && \
sudo chmod +x /usr/local/bin/docker-compose && \
sudo ln -s /usr/local/bin/docker-compose /usr/bin/docker-compose

# 설치 확인
$ docker -v # Docker 버전 확인
$ docker compose version # Docker Compose 버전 확인
```

# S3 (Simple Storage Service) 개념 

Amazon S3는 **Amazon Simple Storage Service**의 약자로 데이터를 객체 단위로 관리하는 오브젝트 스토리지 서비스이다.

S3 = 파일 저장 서비스, 데이터를 온라인으로 오브젝트 형태로 저장하는 서비스

  - HTTP/HTTPS 통한 API 사용

**S3 기능** 

  - 파일 저장 공간으로 사용

  - 정적 웹 사이트 호스팅

# S3 객체 스토리지 특징 

객체 스토리지 = 객체로 된 파일을 다루는 저장소 

S3에 파일을 설치하는 행위는 불가능, 그냥 이미지나 동영상 파일 등만을 저장할 수 있다. 

### S3 장점 

  - S3는 저장 용량이 무한대이고 파일 저장에 최적화, 용량을 추가하거나 성능을 높이는 작업이 필요없다. 
  - 비용은 EC2, EBS로 구축하는 것보다 훨씬 저렴하다 
- **EBS(Elastic Block Store) → SSD/HDD 같은 보조 기억 장치 서비스** 
    - EBS = 블록 저장소, EC2에 붙여서 **OS, DB, 애플리케이션 데이터 저장소**로 사용
  - 별도의 클라이언트 설치없이 HTTP 프로토콜을 통해 파일 업로드/다운로드 처리가 가능 
  - S3 자체로 정적 웹서비스 가능 (html 파일을 스토리지에 저장하고, html 파일에 접근 → 홈페이지) 
  - 동적 웹페이지는 EC2에서 서비스, 정적 웹페이지는 S3를 이용하면 성능도 높이고 비용도 절감할 수 있다. 

### S3 사용 example

  - 클라우드 저장소 (개인 파일 보관, 구글 드라이브처럼 사용) 
  - 서비스의 대용량 파일 저장소 → 이미지, 동영상 (넷플릭스) 
  - 서비스 로그 저장 및 분석

# S3 버저닝(Versioning)

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca88162be0aeca59989167f.png)

```json
파일을 실수로 삭제하고 저장을 해버렸을 경우
S3는 이를 위해 자동화된 백업 관리 기법인 버전 관리 및 생애주기 관리 기법을 제공한다.
 
버저닝(Versioning)은 특정 객체에 여러 버전을 유지하는 수단이다.

파일에 버젼 아이디를 붙임으로서, 
버전 관리를 사용하여 S3 버킷에 저장된 모든 객체의 버전을 보존, 검색 및 복원할 수 있다. 

또한 의도하지 않은 사용자 작업과 응용 프로그램 오류 모두 쉽게 복구할 수 있다.
변경내용을 추적할 수 있으므로 매우 편리하지만 비용을 조심해야한다.
 
aws 매니저에서 버킷을 만들때 기본적으로 비활성화 라서, 직접 활성화 해야한다. 
단, 버킷에서 버전을 사용하도록 설정한 후에는 비활성화 상태로 돌아갈 수 없다. 
대신 버전 관리 일시 중지 설정은 가능하다.
```

### 객체 버전 ID 수정 / 삭제 / 조회 동작 

버킷에 대한 버전 관리를 활성화 하면 저장되는 객체에 대해 고유한 버전 ID가 자동으로 생성되어진다. 

즉, 키값은 동일하지만 버전 ID가 다른 두 객체를 보유할 수 있게 된다. 

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca881b6bdc3dd027611c181.png)

**파일 수정 동작** 

버전 관리를 사용하는 버킷에 객체를 **PUT**할 때 파일을 덮어쓰지 않는다. 

동일한 이름의 객체를 이미 보유하고 있는 버킷에 새 버전의 객체를 PUT할 때 원래 객체는 버킷에 남아 있으며 S3가 새 버전ID를 만들어 버킷에 추가해 위로 올리게 된다. (맨 위에 올려진게 최신 데이터로 인식)

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca881d8b2fff34b0385d028.png)

이 기능을 통해 객체를 덮어쓰거나 삭제하는 것을 방지하고, 객체 이전 버전을 검색할 수 있다.

**파일 삭제 동작**

객체를 **DELETE** 하면, 버킷에 삭제 마커(Delete Marker)를 삽입하게 된다. 

파일을 삭제한 것이 아니다. 삭제 마커를 최상단에 올림으로서 마치 파일이 삭제된 것처럼 효과를 주는 것

→ soft delete 

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca881c9a7f0cfcc4e82e1f2.png)

버전 관리되는 객체를 영구적으로 삭제하려면 버전 ID 자체를 삭제해야 한다. 

**파일 조회 동작** 

기본적으로 **GET** 요청은 가장 최근에 저장된 버전을 검색한다.

만약 최신 버전이 삭제 마커일 때 요청을 하면 **404 Not Found 오류가 반환된다.** 

이때 특정 버전 ID를 지정하여 특정 객체에 대해 GET을 실행할 수 있다.

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca8813bb6fffd227c64ee04.png)

# S3 보안 / 권한 (접근 제어)

```json
S3는 누군가 접속해 내용물을 변조할 수 있기 때문에 S3 버킷의 기본 정책은 private으로 설정되어 있다. 

만일 외부에서 접속해 S3의 버킷을 제어할 필요가 있다면 어떻게 할까?
이때는 버킷을 통째로 public으로 개방하는 것이 아닌 S3 권한 제어를 통해 접근 제어를 설정할 수 있다. 
```

### S3 권한 설정 

  - 사용자를 생성하고 사용자의 버킷 권한 엑세스를 관리하는 **IAM**
  - 권한 있는 사용자에 대해 간단한 개별 객체(오브젝트)를 액세스 가능하게 만드는 **액세스 제어 목록(ACL)**
  - 단일 S3 버킷 내 모든 객체에 대한 권한을 세부적으로 구성하는 **버킷 정책(bucket policy)**
  - 임시 URL을 사용하여 다른 사용자에게 기간 제한 엑세스를 부여하는 **쿼리 문자열 인증(pre-sigined URL)**

### Public Access 

```json
퍼블릭 액세스 권한은 말 그대로 모두에게 액세스 권한을 오픈할 것인지 
아니면 임의의 사용자에게는 접근 권한을 제한할 것인지 설정하는 것
```

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca8813898cdfcabc676fcea.png)

```json
모든 퍼블릭 엑세스 차단을 설정 한 경우 어떤 경우에도 모든 퍼블릭 접속을 차단하게 된다.

4가지 옵션으로 특수한 경우에 퍼블릭 엑세스가 허용되도록 설정이 가능하다.

실무에서는 모든 퍼블릭 엑세스 차단 혹은 ACL을 이용하여 퍼블릭 엑세스 차단해주는 것이 보안에 좋다. 
```

### ACL(Access Control List)

```json
ACL은 버킷이나 객체에 대해 요청자의 권한 허용 범위를 어디까지 설정할 것인가에 대해 간단하게 설정할 수 있다.

여기서 요청자는 일반 퍼블릭한 사용자가 될 수도 있고
계정의 owner, resouce group, 특정 사용자가 될 수 있다.

버켓 주인과 오브젝트 주인이 다를 경우의 권한 설정,
log 저장용 버킷에 대한 권한 설정 등을 설정 할 수 있다.
 
각각의 버킷과 그 속에 포함된 객체는 ACL과 연동된다. 
따라서 ACL로 S3 버킷이나 객체의 접근을 제어하는게 가능하다.

ACL은 IAM이나 버킷 정책에 비해 더 넓은 범위에서 제어할 수 있지만, 
단지 접근 승인을 한 곳과 접근 승인을 받은 곳으로만 나타낼 수 있다. (간단한 것만 설정 가능)
```

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca8818b94abf57fec89d987.png)

### 버킷 정책(Bucket Policy)

```json
Bucket Policy는 버킷을 사용할 권한을 가진 여러 명의 사용자 별로 
각각의 행위에 대한 권한 범위를 설정할 수 있다.

예를 들어 누군가는 읽기만 가능하고 누군가는 읽기, 쓰기 모두 가능한 상태 같이 말이다.

즉, Bucket에 대한 전반적인 권한 설정은 Bucket Policy를 통해 설정된다.
단, 버킷 안의 파일 하나하나의 권한 설정은 불가능하다.
```

**ACL VS Bucket Policy** 

  - ACL과 버킷 정책 모두 버킷에 대한 엑세스를 제한하거나 허용하는 권한 설정이다. 
  - **설정 범위:** 버킷정책은 버킷에 대해서만 권한을 설정할 수 있지만, ACL은 버킷 뿐만 아니라 개별 객체에도 가능하다. 
  - **세분화된 설정:** 버킷정책은 JSON을 통해 세분화된 권한을 설정할 수 있지만, ACL은 버킷 정책만큼 세분화된 엑세스 모드를 제공하지 않는다.  

**Bucket Policy example** 

```json
{
    "Version": "2012-10-17", // Bucket Policy의 문법이 언제 날짜 기준으로 확정된 문법을 사용하는지 → 2008-10-17 버전 후 2012-10-17 버전이 있는데, 그 뒤로는 업데이트가 안됐음
    "Id": "S3PolicyId1", // Bucket Policy의 고유 아이디, 자동으로 부여되는 경우가 많음
    "Statement": [
        {
            "Sid": "IPAllow", // 각 Statement의 고유 아이디. 무슨 역할을 하는 policy인가
            "Effect": "Allow", // 버킷에 대한 명령을 허락(allow)하거나 거부(deny). 특정 사용자에 대해 명령을 제한하거나, 허용하는 식으로 사용
            "Principal": {"AWS": "arn:aws:iam::spark323:user/spark"}, // Bucket Policy의 적용대상 (spark323 아이디의 유저에 대해서)
            "Action": [ // Bucket Policy에서 허용한 Action
                "s3:GetObject", // 객체 가져오는 행동
                "s3:GetBucketLocation", // 버켓 위치를 확인하는 행동
                "s3:ListBucket", // 버켓 리스트를 확인하는 행동
            ],
            "Resource": "arn:aws:s3:::bucketname/*", // 대상이 대는 Bucket에 대한 명세
            "Condition": { // 어떤 조건 하에
                "NotIpAddress": { // 이 IP비허용
                    "aws:SourceIp": "1.1.1.1/32"
                },
                "IpAddress": { // 이 IP허용
                    "aws:SourceIp": [
                        "192.168.1.1",

                }
            }
        }
    ]
```

# S3 요금 정책 

S3는 사용한 만큼만 요금을 지불한다. 

**동일한 리전의 EC2와는 데이터 전송 요금이 발생하지 않으므로 S3와 EC2 리전은 동일하게 설계한다.**

  - 스토리지 요금: 객체 저장 비용(객체 크기, 월에 객체 저장한 기간, 스토리지 클래스에 따라 다르다)
  - 요청 및 데이터 검색: GET, LIST 및 기타 요청에 대한 비용 발생(DELETE 및 CANCEL 요청 무료)
  - 데이터 전송: 특정 케이스를 제외하고 모든 송수신 데이터에 요금 지불

## 6. 실제 S3 서비스 구현

```java
@Service
@Profile("!test")  // 테스트 환경이 아닐 때만 활성화
@RequiredArgsConstructor
@Slf4j
public class S3ServiceImpl implements S3Service {

    private final S3Client s3Client;
    private final S3Properties s3Properties;

    @Override
    public String uploadImage(MultipartFile file, String directory) {
        try {
            String fileName = generateFileName(file.getOriginalFilename());
            String key = directory + "/" + fileName;

            PutObjectRequest putObjectRequest = PutObjectRequest.builder()
                    .bucket(s3Properties.getBucketName())
                    .key(key)
                    .contentType(file.getContentType())
                    .contentLength(file.getSize())
                    .build();

            s3Client.putObject(putObjectRequest,
                    RequestBody.fromInputStream(file.getInputStream(), file.getSize()));

            log.info("이미지 업로드 성공: {}", key);
            return getImageUrl(key);

        } catch (Exception e) {
            log.error("이미지 업로드 실패", e);
            throw new RuntimeException("이미지 업로드에 실패했습니다.", e);
        }
    }

    @Override
    public void deleteImage(String imageUrl) {
        try {
            String key = extractKeyFromUrl(imageUrl);

            DeleteObjectRequest deleteObjectRequest = DeleteObjectRequest.builder()
                    .bucket(s3Properties.getBucketName())
                    .key(key)
                    .build();

            s3Client.deleteObject(deleteObjectRequest);
            log.info("이미지 삭제 성공: {}", key);

        } catch (Exception e) {
            log.error("이미지 삭제 실패: {}", imageUrl, e);
            throw new RuntimeException("이미지 삭제에 실패했습니다.", e);
        }
    }

    @Override
    public String getImageUrl(String key) {
        return String.format("https://%s.s3.%s.amazonaws.com/%s",
                s3Properties.getBucketName(), "ap-northeast-2", key);
    }

    private String generateFileName(String originalFilename) {
        String extension = originalFilename.substring(originalFilename.lastIndexOf("."));
        return UUID.randomUUID().toString() + extension;
    }

    private String extractKeyFromUrl(String imageUrl) {
        // URL에서 키 추출 로직
        String baseUrl = String.format("https://%s.s3.ap-northeast-2.amazonaws.com/",
                s3Properties.getBucketName());
        return imageUrl.replace(baseUrl, "");
    }
}

```

## 8. 컨트롤러 예시

```java
@RestController
@RequestMapping("/api/images")
@RequiredArgsConstructor
@Slf4j
public class ImageController {

    private final S3Service s3Service;

    @PostMapping("/upload")
    public ResponseEntity<Map<String, String>> uploadImage(
            @RequestParam("file") MultipartFile file,
            @RequestParam(value = "directory", defaultValue = "images") String directory) {

        if (file.isEmpty()) {
            return ResponseEntity.badRequest().build();
        }

        try {
            String imageUrl = s3Service.uploadImage(file, directory);

            Map<String, String> response = new HashMap<>();
            response.put("imageUrl", imageUrl);
            response.put("message", "이미지 업로드 성공");

            return ResponseEntity.ok(response);

        } catch (Exception e) {
            log.error("이미지 업로드 실패", e);
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).build();
        }
    }

    @DeleteMapping
    public ResponseEntity<Map<String, String>> deleteImage(@RequestParam("imageUrl") String imageUrl) {
        try {
            s3Service.deleteImage(imageUrl);

            Map<String, String> response = new HashMap<>();
            response.put("message", "이미지 삭제 성공");

            return ResponseEntity.ok(response);

        } catch (Exception e) {
            log.error("이미지 삭제 실패", e);
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).build();
        }
    }
}
```

# 이미지 업로드 방식 5가지 

### 1. BLOB 데이터타입으로 DB에 저장 

**BLOB: Binary Large Object** 

```plain text
이미지, 동영상, 파일, 바이너리 데이터와 같은 큰 데이터를 저장할 수 있는 데이터 타입 
```

**BLOB 종류**

MySQL에는 4가지 BLOB 타입 존재 

| 타입 | 최대 크기 | 설명 |
| --- | --- | --- |
| `TINYBLOB` | 255 바이트 | 아주 작은 바이너리 데이터 |
| `BLOB` | 65KB (2^16) | 일반적인 크기의 바이너리 데이터 |
| `MEDIUMBLOB` | 16MB (2^24) | 중간 크기의 바이너리 데이터 |
| `LONGBLOB` | 4GB (2^32) | 아주 큰 바이너리 데이터 (파일 등) |

**단점** 

  - **I/O 부하:** DB에 큰 바이너리 데이터를 read/write 하면 디스크 I/O와 네트워크 사용량이 커진다. 
  - **쿼리 성능 부하:** 일반적인 텍스트/숫자 컬럼보다 인덱싱이나 검색이 느려지고, 전체 테이블 처리 속도가 떨어질 수 있다. 
  - **캐싱 비효율:** DB의 캐시(InnoDB Buffer Pool) BLOB 데이터까지 캐싱하게 되어 메모리 자원을 낭비 
  - **DB 백업/복구 시간 증가:** 큰 바이너리 데이터를 DB에 저장하면 백업 파일의 크기가 커지고, 복구 시간도 오래 걸린다.
  - **스토리지 비용 증가:** 클라우드 DB에서는 저장 용량에 따라 요금이 부과되는데, BLOB 데이터를 DB에 저장하면 불필요하게 저장 공간 요금이 많이 나올 수 있다.

---

### 2. Base 64 형태로 DB에 저장 

**Base64** 

```plain text
base64: 64진법 
이미지의 이진 데이터를 text 형태로 바꾸는 encoding 방법
이미지를 인코딩 -> base 64 결과물을 데이터베이스에 저장 
```

**Base64는 3바이트(24비트)를 가져와서 6비트씩 나눠서 4개의 문자로 표현** 

| 저장 방식 | 설명 | 최종 저장 용량 |
| --- | --- | --- |
| Base64 + ASCII (1문자 = 1바이트) | 보통 네트워크 전송 시 | 3바이트 → **4바이트** |
| Base64 + UTF-16 (1문자 = 2바이트) | 예: Java 내부 메모리 등 | 3바이트 → **8바이트**  |

**단점** 

  - 바이너리 데이터를 base64로 인코딩하여 변환하면 원래의 이미지 용량보다 더 큰 용량을 가진다. 
  - 바이너리 데이터 ↔ 텍스트 (인코딩/디코딩) 작업이 필요 

---

### 3. 백엔드에서 파일을 저장하고 경로를 DB에 저장 

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca88190805dd7c0ce4acffb.png)

**장점**

  - 백엔드 단에서 파일을 저장 → 이미지의 업로드/다운로드가 빠르다. 
  - 외부 서비스에 대한 의존성 X
  - base64, blob과 다르게 경로만 저장하기 때문에 db에 부담이 없다. 

**단점** 

  - 저장 공간의 제약을 받는다. 
  - 보안 및 백업 처리 
  - 서버에 요청이 많아지면 업로드 및 다운로드의 속도에 영향이 미친다. 
  - I/O bound 프로그램이 되어버림 → 응답 지연 

---

### 4. Cloud Storage에 이미지를 업로드하고 경로를 db에 저장 

![Notion 첨부 파일](/assets/images/notion/26b7d6692ca88132b374fbb0067853f3.png)

```json
이미지를 백엔드/DB에 저장하지 않고 AWS, GCP, Firebase 같은 Cloud Storage에 업로드하는 방식 
Cloud Storage에 업로드된 경로는 DB에 저장 
```

**장점** 

  - CloudStorage 제공하는 편의 기능
- 복제, 백업 기능 
    - 스토리지 확장이 자동으로 이루어지기 때문에, 로컬 저장처럼 용량 걱정이 없다. 
    - **CDN(Content Delivery Network)** 연동 편의
  - **이미지 서버를 따로 둠 → 백엔드 서버의 I/O bound 문제 해결**

**단점** 

  - 추가 네트워크 비용 발생 
  - 클라우드 스토리지 상태에 따라 추가 대역폭 및 시간 소요 
  - 사용량에 따른 비용 발생 
  - 초기 아키텍처 설계에 대한 어려움 
  - 나의 AWS 지식 부족
